## 1. Task 0: Specification of the planning problem

**(a) Initial state:** I = { At(Robot, A), At(Package, A) }

**(b) Goal:** G = { At(Package, C) }. Nothing is required about where the robot ends up.

**(c) Actions available to the robot** (10 ground actions). The map is A — B — C; there is **no** direct link between A and C.
- Move(A, B), Move(B, A), Move(B, C), Move(C, B)
- PickUp(Package, A), PickUp(Package, B), PickUp(Package, C)
- Drop(Package, A), Drop(Package, B), Drop(Package, C)

**(d) Preconditions and effects** (X, Y, L are locations; X–Y connected)

| Action | Preconditions | Positive effects | Negative effects |
|---|---|---|---|
| Move(X, Y) | At(Robot, X) | At(Robot, Y) | ¬At(Robot, X) |
| PickUp(Package, L) | At(Robot, L), At(Package, L) | Holding(Package) | ¬At(Package, L) |
| Drop(Package, L) | At(Robot, L), Holding(Package) | At(Package, L) | ¬Holding(Package) |

No action in the original problem needs a *negative* precondition. The planner supports them anyway, as the prompt required, and Test C uses one.

**Which actions are applicable in I?** The program checks every action (`python planner.py`):

```
Move(A,B)            APPLICABLE
Move(B,A)            not applicable   because At(Robot,B) is false
Move(B,C)            not applicable   because At(Robot,B) is false
Move(C,B)            not applicable   because At(Robot,C) is false
PickUp(Package,A)    APPLICABLE
PickUp(Package,B)    not applicable   because At(Package,B) is false; At(Robot,B) is false
PickUp(Package,C)    not applicable   because At(Package,C) is false; At(Robot,C) is false
Drop(Package,A)      not applicable   because Holding(Package) is false
Drop(Package,B)      not applicable   because At(Robot,B) is false; Holding(Package) is false
Drop(Package,C)      not applicable   because At(Robot,C) is false; Holding(Package) is false
```

Exactly **two** actions are applicable initially: Move(A, B) and PickUp(Package, A).

### Question: is PickUp(Package, A) applicable in I? What about Drop(Package, C)?

- **PickUp(Package, A): yes, applicable.** Its preconditions are At(Robot, A) and At(Package, A). Both are members of I, so I ⊨ Preconditions(PickUp(Package, A)).
- **Drop(Package, C): not applicable.** Its preconditions are At(Robot, C) and Holding(Package). *Neither* is in I: the robot is at A, not C, and it is not holding the package. Under the closed-world assumption, a proposition that is not in the state is false. So I ⊭ Preconditions(Drop(Package, C)). Failing even one precondition would be enough to make it inapplicable.

**Think About It.** An action appearing in the list of available actions only means it *exists* in the domain. Whether it can be executed *now* is a logical question: are all its preconditions entailed by the current state? Here 8 of the 10 actions exist but cannot be performed in I.

## 2. Task 1: Manually constructed plan

**Note on the example in the sheet.** The sheet suggests reasoning about Move(A, B), PickUp(Package, B), Move(B, C), Drop(Package, C). Taken literally, that sequence is **not a valid plan**. After Move(A, B) the robot is at B, but the package is still at **A**. So the precondition At(Package, B) of PickUp(Package, B) is false. The plan checker confirms this:

```
Step 1: Move(A,B): preconditions [At(Robot,A)] hold -> {At(Package,A), At(Robot,B)}
Step 2: PickUp(Package,B) NOT applicable: At(Package,B) is false
```

The robot must pick the package up **at A**, *before* moving. The correct plan is:

**PickUp(Package, A), Move(A, B), Move(B, C), Drop(Package, C)**

| State | Action leading to it | Facts | Precondition check |
|---|---|---|---|
| S0 | (initial) | At(Robot, A), At(Package, A) | |
| S1 | PickUp(Package, A) | At(Robot, A), Holding(Package) | At(Robot, A) ✓, At(Package, A) ✓ |
| S2 | Move(A, B) | At(Robot, B), Holding(Package) | At(Robot, A) ✓ |
| S3 | Move(B, C) | At(Robot, C), Holding(Package) | At(Robot, B) ✓ |
| S4 | Drop(Package, C) | At(Robot, C), At(Package, C) | At(Robot, C) ✓, Holding(Package) ✓ |

S4 ⊨ G, because At(Package, C) ∈ S4. This is also a **shortest** plan. The package must be picked up (1 action), carried over two links because A and C are not connected (2 actions), and dropped (1 action), so at least 4 actions are needed. A unit test confirms by brute force that no sequence of 1, 2 or 3 actions reaches the goal.

## 3. The prompt used with the LLM (Claude)

> I want to implement a simple planning agent in Python.
> Represent a state as a set of logical propositions.
> Each action should contain:
> - a name;
> - positive preconditions;
> - negative preconditions;
> - positive effects;
> - negative effects.
>
> An action is applicable if all of its preconditions are satisfied by the current state. When an action is applied:
> 1. remove its negative effects from the state;
> 2. add its positive effects to the state.
>
> Use breadth-first search to find a sequence of actions that achieves a specified goal.
> The program should also:
> - detect when no plan exists;
> - print the resulting sequence of actions;
> - print the states reached after each action.
>
> Explain the implementation and identify any assumptions you make.
>
> Apply it to this problem. Locations A, B, C; A–B and B–C are connected (both directions), A–C is not.
> Initial state {At(Robot,A), At(Package,A)}; goal {At(Package,C)}.
> Move(X,Y): pre At(Robot,X); add At(Robot,Y); delete At(Robot,X).
> PickUp(Package,L): pre At(Robot,L), At(Package,L); add Holding(Package); delete At(Package,L).
> Drop(Package,L): pre At(Robot,L), Holding(Package); add At(Package,L); delete Holding(Package).

Follow-up prompts:
1. *"Add a function that independently re-executes a given plan from the initial state, checks every precondition, and reports the first action whose preconditions fail and why."*
2. *"For every action in the plan, identify its preconditions and show that those preconditions are satisfied in the state in which the action is executed."* (Task 5)

**Assumptions stated by the LLM:**
- **Closed world:** a proposition not in the state is false.
- Propositions are **ground** strings such as `"At(Robot,A)"`, so no variables appear at planning time. Actions are pre-instantiated for every location and connection.
- An action's **negative effects are removed before positive effects are added**, so a proposition that appears in both lists ends up true.
- Actions are **deterministic**, and the environment is fully observable.
- **All actions have equal cost**, so BFS returns a plan with the fewest actions.
- **Goals are conjunctions of positive propositions**, satisfied when G ⊆ S.
- When the robot holds the package, the package has **no At(Package, ·) fact**; its location is implicitly the robot's.

## 4. The generated Python program

See [`planner.py`](planner.py).

### Think About It: where the specification appears in the code

| Idea | Question | Where in `planner.py` |
|---|---|---|
| **Preconditions** | When is an action applicable? | `applicable(state, action)`: `action.pos_pre <= state and not (action.neg_pre & state)`, i.e. all positive preconditions are in S and no negative precondition is in S |
| **Effects** | How does the state change? | `apply(state, action)`: `(state - action.neg_eff) \| action.pos_eff`, deleting first, then adding |
| **Goal** | When does planning terminate? | `goal_satisfied(state, goal)`: `goal <= state`, checked in `bfs_plan` for each new state. The search also stops with `None` when the frontier is empty (no plan exists). |
| **BFS** | How are alternative plans explored? | `bfs_plan()`: a FIFO `deque` frontier of states, with `parent` as both visited set and back-pointer map. States are explored level by level (all 1-action plans, then all 2-action plans, …), so the first plan found is a shortest one. |

## 6. Task 4: Logic and search

**Completed description:**

```
Current state
     ↓
Check action preconditions        (logic:  S ⊨ Preconditions(a) ?)
     ↓
Apply the action's effects:  S′ = (S − Del(a)) ∪ Add(a)   ← the missing step
     ↓
Generate successor state
     ↓
Search over alternatives          (BFS frontier: which state to expand next)
     ↓
Goal?                             (logic:  S′ ⊨ G ?  If not, continue searching)
```

The missing step is **"if the preconditions are satisfied, apply the action: remove its negative effects and add its positive effects"**. Actions whose preconditions fail are discarded at this point.

**Where each idea is used.**
- **Logical reasoning** is used to decide (1) whether an action is applicable, S ⊨ Preconditions(a); (2) what the new state is, by applying the effect axioms; and (3) whether a state satisfies the goal, S ⊨ G.
- **Search** is used to decide *which* of the possible action sequences to explore, and in which order. BFS keeps a frontier of reached states, expands them level by level, avoids revisiting states, and stops when a goal state is found or the frontier is empty.

**In my own words.** Logic acts as the rules of the game. In every state it tells the planner exactly which moves are legal and what each legal move does to the world. It never decides which move is a *good* idea. Search is the strategy. It systematically tries the legal alternatives (here breadth-first, so shorter plans are tried before longer ones) and uses the logical goal test to recognise success. Neither part is enough on its own. Logic alone can verify one step but cannot find a sequence. Search alone has nothing to search over without the logical successor function. Together they produce a plan that is both *legal* (every step justified by logic) and *found systematically* (by search). In short: **logic determines what is possible; search determines what to try.**

## 7. Task 5 (optional): can the LLM verify its own plan?

**Prompt:** *"For every action in the plan, identify its preconditions and show that those preconditions are satisfied in the state in which the action is executed."*

**LLM's explanation (summarised):**
1. PickUp(Package,A) needs At(Robot,A) and At(Package,A). Both are in the initial state.
2. Move(A,B) needs At(Robot,A). PickUp did not change the robot's position, so it still holds.
3. Move(B,C) needs At(Robot,B), which was made true by Move(A,B).
4. Drop(Package,C) needs At(Robot,C), made true by Move(B,C), and Holding(Package), made true by PickUp and not deleted since.
5. Drop adds At(Package,C), so the goal is satisfied.

**Comparison with the executed transitions.** The program's independent re-execution (`validate_plan`) produced:

```
Step 1: PickUp(Package,A): preconditions [At(Package,A), At(Robot,A)] hold -> {At(Robot,A), Holding(Package)}
Step 2: Move(A,B): preconditions [At(Robot,A)] hold -> {At(Robot,B), Holding(Package)}
Step 3: Move(B,C): preconditions [At(Robot,B)] hold -> {At(Robot,C), Holding(Package)}
Step 4: Drop(Package,C): preconditions [At(Robot,C), Holding(Package)] hold -> {At(Package,C), At(Robot,C)}
Goal SATISFIED in final state {At(Package,C), At(Robot,C)}
```

For this plan the explanation and the computed transitions agree. Prolog also confirms the plan independently (`achieves_goal(...)` is `true`), and Prolog's own search finds the same shortest plan.

**Which should you trust more: (a) the LLM's explanation, or (b) the independently executed state transitions?**
**(b), the independently executed state transitions.** The program applies the stated precondition and effect rules *mechanically and exhaustively* to every fact in every state. Its result is reproducible, and it can be re-checked by other independent tools (the unit tests and Prolog both agree). The LLM's explanation is generated text. It is produced by predicting a plausible justification, not by executing the rules, so it can sound equally convincing whether the plan is right or wrong. The example sequence in the sheet shows the danger. An LLM asked to "explain why Move(A,B), PickUp(Package,B), Move(B,C), Drop(Package,C) is valid" can easily produce a fluent justification and silently assume the package is at B. The executed transitions immediately expose that At(Package,B) is false. The explanation is still useful for *understanding* the plan, but **a generated explanation is not the same as an independent verification**.

## 8. Answers to the "Think About It" questions

- **Task 0, applicability.** An action is applicable only if every precondition is entailed by the current state, not merely because it is in the action list. In I only Move(A,B) and PickUp(Package,A) qualify.
- **Task 2, mapping the spec to the code.** See the table in §4: preconditions → `applicable`, effects → `apply`, goal → `goal_satisfied`, BFS → `bfs_plan`.
- **Task 4, "logic determines what is possible; search determines what to try."** Answered in §6. This is the same architecture as the search algorithms of the previous module. The logical successor function plays the role of the transition function T, and the goal test plays the role of G.
- **Task 7, "Generate → Independent verification".** The Python planner *generates* a candidate plan. Prolog, which shares no code with it and derives conclusions only from the facts and rules of the warehouse, *verifies* it. A proposed Move(a, c) is rejected because nothing in the knowledge base supports it (§9).
- **Task 8, Prolog vs classical logic.** For definite clauses like these, Prolog's answer coincides with logical entailment. But Prolog proves goals by depth-first search with unification and backtracking, uses negation as failure (closed world), and depends on clause order. Its operational behaviour is therefore not identical to classical logic: for example, a left-recursive rule can loop instead of answering.

## 9. Optional extension: Prolog as a logical verifier

All queries were run in **SWI-Prolog 9.0.4**. Output is in `prolog_output.txt`.

### Task 6: results

```
?- can_move(a,b).
true.
?- can_move(a,c).
false.
```

**(a) Why does Prolog return true for can_move(a,b)?**
To prove `can_move(a,b)`, Prolog uses the rule `can_move(X,Y) :- connected(X,Y)`. It unifies X = a, Y = b, which leaves the subgoal `connected(a,b)`. That subgoal matches a fact in the knowledge base, so the proof succeeds.

**(b) Why does it not establish can_move(a,c)?**
The subgoal becomes `connected(a,c)`, and no fact or rule can prove it. The only `connected` facts are (a,b), (b,a), (b,c) and (c,b). Prolog works under the **closed-world assumption** (negation as failure): what cannot be derived is reported as false. Note that `connected` is not transitive here. The facts say nothing like "if a–b and b–c then a–c", so the robot cannot move *directly* from a to c, even though it can *reach* c in two moves.

**(c) What is the relationship between the rule `can_move(X,Y) :- connected(X,Y)` and Connected(X,Y) → CanMove(X,Y)?**
The rule *is* that implication, written backwards. `Head :- Body` means "Head if Body", i.e. Body → Head. The variables are implicitly universally quantified, so the clause represents ∀X ∀Y (Connected(X,Y) → CanMove(X,Y)). Querying `can_move(a,b)` asks whether CanMove(a,b) follows from the knowledge base. Prolog proves it by applying the implication (modus ponens) to the fact Connected(a,b).

### Task 8: results

```
?- reduce_speed.
true.
```

**Why the query succeeds.** To prove `reduce_speed`, Prolog finds the rule `reduce_speed :- slippery` and sets up the subgoal `slippery`. The rule `slippery :- wet_road` gives the subgoal `wet_road`, and `wet_road` is a fact, so it succeeds. Each rule's body is therefore proved, and the original query is true. SWI-Prolog's trace shows exactly this chain:

```
Call: reduce_speed → Call: slippery → Call: wet_road
Exit: wet_road     → Exit: slippery → Exit: reduce_speed
```

**As a sequence of implications:**

  WetRoad (fact)  ⇒  [WetRoad → Slippery] (rule)  ⇒  [Slippery → ReduceSpeed] (rule)  ⇒  ReduceSpeed (conclusion)

In other words: WetRoad, and WetRoad → Slippery, give Slippery (modus ponens). Then Slippery, and Slippery → ReduceSpeed, give ReduceSpeed (modus ponens).

### 7.2 Reflection (Prolog)

1. **Difference between a Prolog fact and a Prolog rule.** A fact (`wet_road.`, `connected(a,b).`) states something that is unconditionally true. It has a head and no body. A rule (`slippery :- wet_road.`) states that its head is true *if* its body can be proved. It is a conditional, an implication, and lets new facts be *derived* from existing ones.
2. **How a query corresponds to asking whether something follows from a knowledge base.** A query `?- G.` asks: "is G a logical consequence of the facts and rules?", i.e. KB ⊨ G. Prolog answers by trying to construct a proof of G (by resolution: unification and backtracking over the clauses). `true` means it found a proof. `false` means it could not, which under the closed-world assumption is treated as "G does not follow".
3. **Why use a Prolog program to verify a plan generated by a Python program?** The two systems are independent. The Prolog verifier is a short, declarative restatement of the domain rules (connections, preconditions, effects) that can be read and checked by a human, and it shares no code with the planner. If the Python program has a bug (for example, it forgets a precondition or allows a move between unconnected locations), the plan it produces will fail the Prolog check. Agreement between the two gives much stronger confidence than either one alone.
4. **What advantage does an independent verifier provide when the plan was generated with LLM help?** LLM-generated code and explanations can be plausible but wrong, and the LLM cannot be relied on to detect its own mistakes. Its "verification" is just more generated text. An independent verifier applies the *specified* rules mechanically. It does not depend on the LLM's reasoning, and it gives a definite, reproducible yes/no. It turns "the plan looks right" into "the plan is provably consistent with the domain knowledge". This is the *Generate → Independent verification* architecture: the AI proposes, the logic checks.

### Reflection questions

1. **Why is it useful to specify action preconditions and effects before asking an LLM to write the planner?**
They *are* the problem. If they are left vague, the LLM must guess. It might let the robot move between A and C directly, forget to delete At(Package, L) when the package is picked up, or treat the robot's location as the package's location. Writing them precisely first gives an unambiguous prompt. It also gives a specification to test the generated code against, and makes clear what "correct" means before any code exists.

2. **Example of an error if the planner failed to check an action's preconditions.**
The planner could return the one-step "plan" [Drop(Package, C)] from the initial state. That would claim the package is at C while the robot is at A and not even holding it. It could also return Move(A, B), PickUp(Package, B), … (picking up a package that is not there), or Move(A, C) (driving between unconnected locations). Each of these "achieves" the goal on paper but is physically impossible.

3. **Why is a plan that "looks reasonable" not necessarily a valid plan?**
Validity is a precise logical property: every action's preconditions must hold *in the exact state in which it is executed*, and the final state must entail the goal. A plan can look sensible to a human because its actions are the right kinds and in roughly the right order, yet fail that check. The sheet's own example (Move(A,B), PickUp(Package,B), …) looks reasonable and is invalid, because the package is still at A. Similarly Move(A,B), Move(B,C) "gets to C", but only the robot gets there.

4. **What did the LLM contribute to the implementation?**
Fast, clean, well-structured code. A good representation choice (frozensets, so states are hashable and can be stored in a visited set). A correct BFS with path reconstruction. A clear explanation of the implementation and an explicit list of its assumptions (closed world, delete-before-add, ground propositions). It also drafted test code and the Prolog extensions. It saved most of the typing and some of the design detail.

5. **What did you have to verify independently?**
- That `applicable` really checks *all* positive *and* negative preconditions, and that `apply` deletes before it adds (both unit-tested directly).
- That the returned plan is valid step by step, and that it is shortest (brute force over all shorter sequences).
- That impossible problems report "No plan found" and terminate.
- That the goal test distinguishes the robot being at C from the package being at C.
- The LLM's verbal explanation of the plan, against the executed transitions and against Prolog.
- That the Prolog queries really give the expected answers, by running SWI-Prolog.

6. **In this laboratory, where is logical reasoning being used?**
In the planner: in testing whether an action is applicable (S ⊨ Preconditions(a)); in computing the successor state from the effect axioms; and in the goal test (S ⊨ G). In the independent plan checker, which re-derives each state. And in Prolog, where queries are answered by inference (modus ponens via resolution) from facts and rules: `can_move`, `valid_move`, `achieves_goal` and the `reduce_speed` chain.

7. **How is planning related to the search algorithms studied in the previous module?**
Planning *is* state-space search. The planning problem (I, A, G) maps directly onto the search problem (S, A, T, s0, G, c). States are sets of propositions, s0 = I, the transition function is Apply(S, a) (defined only when S ⊨ Preconditions(a)), the goal test is G ⊆ S, and each action costs 1. The planner uses exactly the BFS of the previous module, so it inherits its properties: complete, and optimal in the number of actions. A* with a planning heuristic (e.g. the number of unsatisfied goal propositions) could be used in exactly the same way for larger problems. What logic adds is a *general, declarative* way of describing states and actions, so the same search code works for any domain written as preconditions and effects.

## Takeaway

**Understand → Specify → Generate → Execute → Verify.** The LLM generated a correct planner quickly, but the confidence in it comes from the independent checks: the step-by-step validator, the unit tests, the brute-force optimality check, and Prolog's separate verification. The LLM's explanations do not provide that confidence.
